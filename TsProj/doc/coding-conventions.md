# TypeScript 编码约定

## 基础约定

- 遵循 `tsconfig.json` 的 strict 模式和现有 ESLint 配置，不使用类型断言掩盖不明确的 owner 或生命周期。
- 命名表达领域含义与单位；布尔值使用可判断的状态名称，时间和距离在易混淆处写明单位。
- 文件和模块保持单一主要职责；抽取依据是稳定语义、生命周期或复用边界，不是单纯缩短文件。
- 不直接修改 `dist/`；生成结果只由 `npm run build` 产生。

## 类型与状态

- 优先使用可判别联合表达有限状态，不用互相矛盾的多个布尔值模拟状态机。
- 对外输入在边界校验，进入核心系统后保持类型和不变量明确。
- `undefined` 表示合法缺席时才使用；常态必需依赖直接表达为必需类型，短暂初始化状态在最近 owner 收口。
- 不使用 `any` 绕过 PuerTS 或 Unity 类型缺口；缺失类型应在 `types/` 中以最小范围补齐。
- 稳定身份使用 GUID 或明确 ID，不使用数组下标、显示名称或 Unity 实例引用充当持久身份。

## ECS 与游戏逻辑

- Component 只保存数据；构造默认值集中在 `ComponentType` 工厂。
- System 通过查询处理实体，不把具体实体硬编码进通用系统。
- 一个事实由一个组件或 owner 持有；缓存派生值前先确认独立语义、生命周期或性能收益。
- 游戏命令表达输入意图，校验与结论由权威系统完成。
- 跨模块事件和状态变化要有清晰的发布者、消费时机和清理时机。

## 集合与高频路径

- 只需遍历、判断、计数或寻找单个结果时，不为调用方便先复制、包装或排序整个集合。
- 循环内避免重复 `query`、线性搜索、字符串拼接和不必要的临时对象；必要缓存需要明确失效规则。
- 修改迭代中的集合时使用延迟命令、待销毁标记或稳定快照，避免跳项和同帧不一致。
- 选择数据结构时说明真实访问模式；不要为可能出现的规模提前引入复杂索引。

## Unity/PuerTS 边界

- Unity API 只出现在明确命名的 adapter、presentation 或 `src/ui/` 模块中。
- 跨栈 callback 优先使用可保存引用的函数，并在 owner 销毁时用同一引用注销。
- Unity 对象在使用前考虑销毁状态；长期持有引用时明确由谁创建和销毁。
- C# 与 TypeScript 之间保持粗粒度生命周期或稳定契约，不为单一按钮或示例动作扩展专用桥接函数。

## 错误与释放

- 无法满足状态不变量时抛出带操作和当前状态的错误，不静默跳过常态必需步骤。
- 可预期的输入无效由领域结果表达，不用异常承担普通控制流。
- `dispose()` 保持幂等；多个资源释放时尽量完成全部清理并保留第一个错误。
- 初始化中途失败必须回滚已经创建或注册的资源。
- 不吞掉错误；需要降级时记录足够定位 owner 的上下文。

## 注释与文档

- 注释解释不明显的约束、顺序或取舍，不复述代码表面行为。
- 公共契约发生变化时优先更新 owner 文档，而不是在多个调用点复制说明。
- 局部 README 可以说明目录导航和示例，但不能覆盖 `doc/` 中的稳定规则。
